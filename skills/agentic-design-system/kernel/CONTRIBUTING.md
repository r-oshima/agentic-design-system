# Contributing

このDesign Systemの定義を追加・変更・廃止するときの規則。

この規則に従い、lintを通した変更は、UIを作る作業の途中でも行ってよい。変更が正しいかは規則とlintで担保し、人の確認は[人に確認する変更](#人に確認する変更)だけに限る。構造の規則は[ARCHITECTURE](ARCHITECTURE.md)にある。

## 変更の進め方

1. 既存の定義で表せないか確認する。
2. 下の基準に従って定義を追加・変更する。
3. 関係するファイルを同じ変更で揃える。色の組み合わせは[contrast.json](contrast.json)、Component・Pattern・Foundationの一覧はREADMEのIndex、観察した内容はreferences。READMEのIndexに見本の行がある場合は、見本を作り直して`node scripts/sample.mjs --stamp`で指紋を更新する（[ARCHITECTURE](ARCHITECTURE.md#見本)）。
4. `node scripts/lint.mjs`を通す。lintを変更した場合は`node --test scripts/lint.test.mjs`も通す。
5. 必要な記録を残す（[記録](#記録)）。
6. UIの作業に戻る。作業の最後に、追加・変更した定義を一覧で報告する。

## 人に確認する変更

次の変更は、行う前に人に確認する。何を変えるか、なぜ必要か、他の選択肢を示す。これ以外の変更は確認しなくてよい。ユーザーのフィードバックから行う変更は、[フィードバックを受けたとき](#フィードバックを受けたとき)の手順で範囲を確かめていれば、確認済みとして扱う。

| 変更 | 理由 |
| --- | --- |
| READMEのDesign Principlesにある原則の変更・削除と、対象の変更。既存の原則と矛盾しない原則を足すだけの変更は除く | 全体の方向性が変わる |
| ARCHITECTUREとlintの規則の変更。カテゴリやpropertyの語彙を足すだけの変更と、文書にある規則を確かめるlintを足すだけの変更は除く | 他の変更の正しさを判断する基準が変わる |
| `stable`な定義の値の変更、`deprecated`への変更、削除 | 使っている画面の見た目や動きが変わる |
| 状態を`stable`に上げる | 以後の変更に確認が必要になる |
| `contrast.json`への例外の追加 | 品質の基準を下回ることを認める |
| リファレンスの追加と、その用途・`fidelity`の変更 | 何を材料に設計するかが変わる |

## 判断できないとき

UIを作っていて、Design Systemの定義だけでは判断できない場合は、次の順で進める。足りないのは部品に限らない。

判断した内容は、UIに反映するだけで終わらせず、必ずDesign Systemにも定義として残す。次に同じ判断が必要になったとき、Design Systemの中で答えが見つかるようにするため。リファレンスを調べた場合も同じで、見ただけで済ませない。

1. 何が足りないかを、下の表で分類する。
2. Design Principles、Foundation、[decisions](decisions/)で判断できないか確かめる。
3. `references/`にリファレンスがあれば、[リファレンスを使う](#リファレンスを使う)に従って調べる。リファレンスに該当するものがない場合や、リファレンスがない場合は、Design Principlesと既存の定義を基に設計する。
4. 下の表の反映先に、[変更の進め方](#変更の進め方)に従って定義を追加する。

| 足りないもの | 例 | 反映先 |
| --- | --- | --- |
| 値 | 合う間隔の段階がない | Token |
| 選び方の基準 | グループの間にどの余白を使うか | Foundation |
| 部品 | 入力欄がない | Component |
| 部品のふるまい | 入力エラーをどこにどう出すか | ComponentのUsage・Interaction |
| 画面の構成 | 一覧と詳細をどう配置するか | Pattern |
| 画面をまたぐ判断 | 一覧の行をカードにするか | READMEのDesign Principles |

Design Principlesには、既存の原則と矛盾しない原則なら確認せずに足してよい。既存の原則を変える・消す場合は[人に確認する](#人に確認する変更)。

## フィードバックを受けたとき

ユーザーから画面へのフィードバックを受けたら、その画面だけを直して終わらせず、次の順で進める。同じ指摘を別の画面で繰り返させないため。

1. **何についての指摘かを分ける。**

   | 指摘の対象 | 例 | 反映先 |
   | --- | --- | --- |
   | 画面がDesign Systemに従っていない | 指定と違う余白になっている | 画面だけを直す |
   | 定義の値や選び方 | ボタンの色が薄い、行の間隔が狭い | Token、Foundation、ComponentのUsage・仕様 |
   | 定義が足りない | この状態を表す見た目がない | [判断できないとき](#判断できないとき)の表の反映先 |
   | 方向性 | 全体にもっと落ち着いた印象にしたい | READMEのDesign Principles |

2. **影響する範囲を確かめる。** 定義を変えると他の画面にも効く場合は、どの画面に効くかをユーザーに示し、全体に効かせるか、この画面だけにするかを聞く。
   - 全体に効かせる場合は、定義を変える。
   - この画面だけにする場合は、その用途を表すVariation、Component Token、またはSemanticを足す。生の値は書かない。
3. **反映する。** [変更の進め方](#変更の進め方)に従う。手順2でユーザーが範囲を選んだ変更は、[人に確認する変更](#人に確認する変更)に当たっても、確認済みとして扱う。
4. **記録する。** 方向性の指摘や、複数の選択肢から選んだ場合は、ADRに指摘の内容と選んだ範囲を書く。

## Tokenの追加

- 必要な値が既存のTokenとほぼ同じなら、新しいTokenを作らず既存のTokenを使う。目安は、色なら色差（CIEDE2000）が1未満、寸法（字間を含む）なら差が1px未満。リファレンスの値から外れた場合は、referencesに差を記録する。
- まず、用途を表すSemanticを追加できないか考える。名前は、他の部品でも使える用途名にする。
- 新しい値が必要なら、Primitiveに段階を追加し、Semanticからそれを参照する。色の場合、スケール（50、100〜900、950）の間に置く段階は`experimental`にする。
- まだ使わない段階を予約としてPrimitiveに置く場合は、人に確認して`stable`にする。
- 寸法系（Space、Size、Radius）は既存の段階から選ぶ。どの段階も合わない場合だけ段階を追加する。
- 色のSemanticはlightとdarkの両方に追加する。追加した色を重ねて使う組み合わせを`contrast.json`に追加する。
- 新しいカテゴリを足したら、そのカテゴリのFoundationを追加する。Semanticを追加したり用途を変えたりしたら、該当するFoundationの選び方も直す。
- 追加したTokenの状態は`experimental`にする。

## 合うTokenがない指定を表す

仕様の`token`には必ずToken名を書く。合うTokenがない指定に出会ったら、文章や生の値で書かず、次の順で考える。

1. **その値の役割を言葉にする。** 「2px」や「余白」ではなく、「focusの外周を部品から離して描く距離」のように、値が何のためにあるかで言う。
2. **分類を決める。**

   | その値は | 分類 | 表し方 |
   | --- | --- | --- |
   | 他の部品でも同じ役割で使い、役割ごとまとめて変えたい | 役割系 | Primitiveに段階を追加し、役割名のSemanticから参照する |
   | 部品の大きさや間隔のように、段階そのものを選ぶ | 寸法系 | Space・Size・Radiusに段階を追加する |
   | その部品の中でしか意味を持たない | Component Token | `tokens/component/<name>.json`に追加する |

3. **値が同じでも、役割が違うTokenを流用しない。** 流用すると、片方の役割だけを変えたいときに分けられなくなる。
4. **値の形にとらわれない。** 負の値や、既存のカテゴリにない単位の値でも、Primitiveとして定義できる。
5. **足りない語彙は足す。** 新しいカテゴリが必要なら、ARCHITECTUREのカテゴリの分類と、lintのカテゴリ・段階名の一覧に追加する。仕様の`property`が足りなければ、`scripts/spec.mjs`の一覧に追加する。語彙を足すだけなら人に確認しなくてよい。

例：Tabsのfocusの外周は、部品の内側に描く（offset -1px）。これは余白ではなく「focusの外周を描く位置」という役割の値で、Buttonの外側に描く2pxと同じ役割を持つ。そこで役割系のカテゴリ`focusOffset`を追加し、Primitiveに`offset.-1`と`offset.2`、Semanticに`focusOffset.inside`と`focusOffset.outside`を定義した。Buttonがそれまで使っていた`space.2`も、余白ではないため`focusOffset.outside`に置き換えた。

## Component・Patternの追加

- 作っている画面で必要になったときに追加する。将来使いそうという理由では作らない。
- 既存のComponentのVariationで表せないか確認する。役割・構造・操作の仕方が違えば別のComponentにし、見た目や大きさの違いはVariationにする。
- その時点で必要なVariationと状態だけを定義する。
- Patternは、同じ画面の構成が2つ以上の画面で必要になったときに追加する。
- 文書と仕様は[Componentの文書と仕様](ARCHITECTURE.md#componentの文書と仕様)に従い、READMEのIndexに追加する。状態は`experimental`にする。

## リファレンスを使う

`references/`のリファレンスは、Design Systemに足りない定義を補う材料にする。[判断できないとき](#判断できないとき)の流れの中で使う。

- リファレンスの「見る画面」から、足りないものに対応する箇所を探す。対象は部品に限らず、画面の構成、ふるまい、余白や文字の使い方なども含む。ページの調べ方は使える道具によって変わるため、この文書では定めない。
- 必要なページが一覧になければ、同じリファレンスの中のページとして「見る画面」に追加する。
- 調べるときは、リファレンスの「用途」に書いた範囲と操作の制限を守る。
- Foundationの選び方やDesign Principlesとして取り込む場合は、複数のページで同じ使い方をしているか確かめる。1つのページにしか現れない特徴は、その部品やPatternの仕様にとどめる。
- 観察した内容は、referencesの対象ごとの節に記録する。採用した定義と、採用しなかった値とその理由を書く。
- 計測値の扱いは、リファレンスの`fidelity`（どれだけ似せたいか）と、計測値の確かさ（どれだけ正確に取れたか）で決める。

  | fidelity | 意図 |
  | --- | --- |
  | `inspire` | 参考にするが、同じにすることにはこだわらない |
  | `match` | できる限り同じ見た目にする |

  | 値の確かさ | 取り方 |
  | --- | --- |
  | 指定値 | 実装の指定から読んだ、正確な値（Webのcomputed style、CSS変数など） |
  | 推定値 | 見た目から測った、誤差のある値（スクリーンショット、色の計測ツール、OSのアクセシビリティの検査ツールなど） |

  | fidelity | 指定値 | 推定値 |
  | --- | --- | --- |
  | `inspire` | 既存の段階に寄せる。近い段階がない場合だけPrimitiveを追加する | 同左 |
  | `match` | 計測値をPrimitiveとして入れる。既存の段階に寄せるのは、見分けられない差（[Tokenの追加](#tokenの追加)の目安）の場合だけ | 計測の誤差の範囲に収まる差は、既存の段階に寄せる。誤差まで再現するために段階を足さない |

  `match`で計測値から外れた場合は、すべて理由をreferencesに書く。`inspire`では計測は必須にしない。

- どちらの`fidelity`でも、「借りないもの」は持ち込まない。READMEのDesign Principlesも上書きしない。
- 計測値がこのDesign Systemの規則と食い違う場合は、規則を優先する。再現を優先したい場合は、人に確認したうえで例外として記録し、ADRに理由を残す。

## 状態の変更

| 変更 | 条件 | 人の確認 |
| --- | --- | --- |
| `experimental`の変更・削除 | 参照している定義を同じ変更で直す | 不要 |
| `experimental` → `stable` | プロダクトのコードで2つ以上の画面から使われている（予約するPrimitiveを除く）。参照するTokenがすべて`stable`。色の組み合わせが`contrast.json`にある | 必要 |
| `stable` → `deprecated` | `$deprecated`に代わりの定義を書く | 必要 |
| `deprecated`の削除 | 参照しているものがすべて代わりの定義へ移っている | 必要 |

### 状態を見直す

プロダクトのコードが増えてきたら、または頼まれたら、Tokenの使われ方を確かめる。

1. `node scripts/usage.mjs <プロダクトのコードのフォルダ>...`を実行する。次の一覧が出る。
   - `experimental`のうち、2つ以上のファイルで使われているもの
   - `deprecated`なのに、まだ使われているもの
   - `experimental`のうち、プロダクトのコードで使われていないもの
2. 1つ目の一覧は、`stable`に上げる候補にする。上の表の条件を確かめる。ファイルの数は画面の数と同じとは限らないので、実際の画面で確かめる。そのうえで、まとめて人に確認する。
3. 2つ目の一覧は、`$deprecated`に書かれた代わりの定義へ、使っている箇所を移す。
4. 3つ目の一覧は、削除を検討する。ComponentやPatternの仕様、またはほかのTokenから参照されているもの（一覧に注記が付く）は、間接的に使われているか、まだ画面が作られていないだけなので残す。

`usage.mjs`は、Token名をそのまま（`color.text.default`）か、`-`や`_`でつないだ形（`--color-text-default`）で探す。プロダクトがほかの形の名前を使っている場合は、その形で検索して確かめる。

## 規則をlintで確かめる

- 機械で確かめられる規則（参照、命名、コントラストなど）は、文書に書くだけでなく、lintとそのテストで確かめる。文書だけに書くのは、判断が必要な規則に限る。
- 文書にある規則が守られずに2回以上直した場合は、その規則をlintで確かめられないか検討する。
- 文書にある規則を確かめるlintを足すだけなら、規則は変わらないので人に確認しなくてよい。lintで文書にない規則を作る場合は、[人に確認する変更](#人に確認する変更)に当たる。
- lintのエラーのメッセージには、直し方を書く。

## 記録

| 記録 | 残す場合 | 場所 |
| --- | --- | --- |
| ADR | 複数の選択肢から1つを選んだ。リファレンスの値から外れた。原則や規則を変えた | `decisions/NNNN-<kebab-case>.md` |
| CHANGELOG | `stable`な定義を変更・廃止・削除した | `CHANGELOG.md`。最初に記録するときに作る |

ADRは`状態（採用日）`、`## 状況`、`## 決定`、`## 結果`で構成する。状態は`採用`か、後のADRで覆した場合の「NNNNで置き換え」（NNNNは後のADRへのリンク）にする。一部だけ覆した場合は、どこを置き換えたかを状態の後に書く。`experimental`な定義の追加・変更は、どちらにも記録しなくてよい。経緯はGitで追う。
