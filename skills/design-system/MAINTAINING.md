# このSkillを改善する

このSkillを継続的に改善する人のための文書。各プロジェクトで運用して得た改善を、次に作るDesign Systemに活かしたいときに読む。プロジェクト用のDesign Systemを作る人と運用する人は読まない。

始める前に、直す対象が「このSkill自体」であることをユーザーに確かめる。プロジェクトのDesign Systemを直す依頼なら、[operate.md](operate.md)で扱う。同じリポジトリにSkillとDesign Systemがある場合は、特に確かめる。

## 考え方

- このSkillは、Design Systemを作る雛形である。作ったあとは、そのプロジェクトのREADME、ARCHITECTURE、CONTRIBUTING、`scripts/`だけで運用が完結する。運用で使いにくくなった場合は、Skillではなく、そのプロジェクトのDesign Systemを直す。
- Skillから各プロジェクトへ、更新を届けることはしない。プロジェクトは写した時点から独立して育つ。
- 流れるのは逆向きである。プロジェクトで構造を改善したら、その改善を大元のSkillに取り込み、次に作るDesign Systemを良くする。

## 構成

| 場所 | 内容 | プロジェクトへの渡し方 |
| --- | --- | --- |
| `kernel/` | ARCHITECTURE、CONTRIBUTING、`scripts/`（lint、テスト、`usage.mjs`、`sample.mjs`など） | `init.mjs`が写す。以後はプロジェクトのもの |
| `templates/README.md` | READMEのひな形 | `init.mjs`が写す。プロジェクトが書き換える |
| `create.md`、`guides/` | 作るときの手順と判断の材料 | 写さない。作るときにだけ読む |
| `scripts/` | 作るときにだけ使う道具（`init.mjs`、`color-scale.mjs`、`color.mjs`） | 写さない |
| `operate.md` | Skillを入れた環境での運用の入口 | 写さない。規則の正本はプロジェクトの文書にある |

運用に必要な道具や規則は`kernel/`に入れる。Skillがなくても運用できるようにするため。

## 改善の進め方

1. 依頼から、元のプロジェクトと、取り込む内容（どの規則、どの仕組み、どの文書か）を読み取る。足りなければ、ユーザーに確かめる。
2. 元のプロジェクトで、その内容がどこに入っているかを調べる。`node scripts/init.mjs --check <Design Systemのフォルダ>`と`diff`は、そのための道具である。違いはプロジェクトで育った結果であり、全部を取り込む対象ではない。依頼された内容だけを取り出す。
3. 取り込む形を考える。そのプロジェクトだけの事情（プロダクトの内容、リファレンス、Token、プロジェクト独自のlintの規則）を除き、他のプロダクトでも必要な形にする。プロジェクトの実装をそのまま写せないときは、取り込む形をユーザーに示して確かめる。
4. `kernel/`、`guides/`、`create.md`を直す。元のプロジェクトは変えない。`kernel/`は、どのプロジェクトとも一致しなくてよい。
5. 試す。新しい場所で`create.md`に従ってDesign Systemを作り、lintとテストが通ること、作った画面に問題がないことを確かめる。リファレンスがある場合とない場合の両方を試す。
6. 試して分かったことは、手順4に戻って直す。

## 守ること

- `kernel/`は、どのプロジェクトのコピーでもない。プロジェクトごとにlintや規則が別々に育つ前提で、共通で必要なものだけを持つ。
- `kernel/`の中のlintとテストは、`kernel/`だけでも通る状態を保つ。
- 作るときにだけ必要な内容を`kernel/`に入れない。プロジェクトの文書が、Skillの存在を前提にしないようにする。
- 特定のプロダクトやリファレンスの名前を、`kernel/`、`guides/`、`create.md`に入れない。
